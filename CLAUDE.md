# MedEase

Healthcare web app built with Next.js (App Router), TypeScript, Tailwind CSS v4, and shadcn/ui.

@AGENTS.md

## Commands

```bash
npm run dev           # start dev server
npm run build         # production build
npm run lint          # ESLint
npm run typecheck     # TypeScript, no emit
npm run format        # Prettier (also sorts Tailwind classes)
```

Run `lint`, `typecheck`, and `build` before every commit. All three must pass.

## Project structure

```
src/
  app/                  Routes only. Pages and layouts stay thin and compose feature components.
  components/
    ui/                 shadcn/ui primitives. Generated by the CLI.
    layout/             App shell: header, footer, container, theme toggle.
    shared/             Reusable composites used by more than one feature.
    providers/          Client context providers, combined in AppProviders.
  features/<name>/      Everything for one feature, e.g. appointments, prescriptions.
    components/         UI for the feature.
    actions/            Server Actions.
    hooks/              Client hooks.
    schemas/            Zod schemas (shared by forms and server validation).
    data/               Static data and data-access functions.
    types.ts            Feature types.
  config/               App-wide configuration (site metadata, navigation).
  hooks/                Hooks shared across features.
  lib/                  Framework-agnostic helpers (utils, formatters, clients).
  types/                Types shared across features.
```

Only create a folder when it has something in it.

## Rules

### Components

- Build every feature from small, reusable components. Never put a whole feature in one file or inline large blocks of JSX in a page.
- Check `components/ui`, `components/shared`, and the feature folder before writing a new component. Reuse or extend what exists instead of duplicating it.
- When a component is needed by a second feature, move it to `components/shared`.
- One component per file. File names are kebab-case (`appointment-card.tsx`), components are PascalCase named exports. No default exports except where Next.js requires them (`page.tsx`, `layout.tsx`, etc.).
- Keep components focused. If a file goes past ~150 lines or does more than one job, split it.
- Pass data in through props. Keep data fetching in Server Components or Server Actions, not in presentational components.
- Do not hardcode copy or lists inside JSX when it belongs in `config/` or a feature `data/` file.

### shadcn/ui

- Add primitives with `npx shadcn@latest add <component>`. Do not hand-write a primitive that shadcn provides.
- Avoid editing files in `components/ui`. Build variants by composing them in `shared/` or feature components. If a change to a primitive is unavoidable, keep it minimal.
- Components use Base UI (`@base-ui/react`). Use the `render` prop instead of `asChild`. For links styled as buttons, apply `buttonVariants()` to `next/link`.
- Use `cn()` from `@/lib/utils` to merge class names.

### Styling

- Tailwind utility classes only. No inline styles, no CSS modules, no new global CSS unless it is a design token.
- Use theme tokens (`bg-background`, `text-muted-foreground`, `bg-primary`, etc.). Never hardcode hex colors.
- Every screen must work in light and dark mode and from 360px width up (mobile first).

### Next.js and React

- Server Components by default. Add `"use client"` only to the smallest component that needs state, effects, or browser APIs.
- Use Server Actions for mutations. Validate every input on the server with Zod, even if the form validates on the client.
- Use `next/link`, `next/image`, and `next/font`. Export `metadata` (or `generateMetadata`) from every page.
- Add `loading.tsx` and `error.tsx` for routes that fetch data.
- Read environment variables through one validated module, never `process.env` scattered across files. Never expose secrets with `NEXT_PUBLIC_`.

### TypeScript

- Strict mode stays on. No `any`, no `@ts-ignore`. Use `unknown` and narrow it.
- Derive types from Zod schemas with `z.infer` instead of declaring them twice.
- Use the `@/` import alias. No deep relative imports like `../../..`.

### Healthcare data

- Treat all patient data as sensitive (PHI). Never log it, never put it in URLs or query strings, and never store it in `localStorage`, `sessionStorage`, or cookies readable by the client.
- Check authentication and authorization on the server for every request and action. Hiding a button is not access control.
- Do not show raw error messages or stack traces to users.
- Do not present app content as medical advice.

### Accessibility

- Target WCAG 2.1 AA. Use semantic HTML, label every form field, give icon-only buttons an `aria-label`, and mark decorative icons `aria-hidden`.
- Everything must be usable with a keyboard and have a visible focus state.

### Git

- Small, focused commits. Write messages in the imperative mood, e.g. "Add appointment booking form".
- Do not add co-author trailers, tool attribution, or generated-by notes to commits or pull requests.
